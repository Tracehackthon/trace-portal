# 工作阶段的原生 Agent 承接

> 用户仍然在 Codex 等原生 Agent 里工作，Trace 在旁边让他看见：过去想清楚的东西怎样来到这里，这次做过之后又改变了什么。

本文属于[产品界面与交互设计](README.md)中的工作界面设计，承接[工作阶段](../产品交互链路/工作阶段/正在做一件事时.md)、[实践想法的接续](../产品交互链路/工作阶段/实践想法的接续.md)和[功能候选与使用方式](../产品功能与交互方案/功能候选与使用方式.md)。

这里先讨论用户看见什么、能做什么，不展开 Skill、上下文包和宿主接入的技术底层，也不代表已经验证所有原生 Agent 都能以相同方式承接。

## 工作 UI 的位置

> 原生 Agent 是工作主场，Trace 是贴在工作现场旁边、可以逐渐展开的“工作接续层”。

当前任务的理解、执行、检查与交付仍由 Codex、Claude Code、dsh 等原生 Agent 和原有工具承担。Trace 不建立第二个工作聊天，也不要求用户先进入 Trace 整理知识，再回到原生 Agent 做事。

工作界面围绕四件事展开：

1. 我现在在哪里工作；
2. 这次带回来了什么；
3. 这些内容是否真的影响了工作；
4. 这次工作又产生了什么值得接回去的东西。

形成一条连续轨迹：

**过去形成的理解 → 当前工作 → 实际做法与结果 → 新发现回到原问题**

## 当前工作区域：先让用户知道 Trace 跟着哪里

当用户正在 Codex 中打开某个项目时，收起的悬浮入口可以只显示：

> Codex · harness

展开后再看到三个层次：

- **宿主 Agent**：Codex、Claude Code、dsh 等；
- **当前项目或工作空间**：例如 `harness`；
- **当前任务或对话**：用户此刻具体正在做什么。

只显示 Agent 和项目还不够。同一个项目里可能同时存在设计工作交互、修改文档、实现悬浮窗和修复 Bug，真正决定哪些理解与经验相关的是当前任务。

点击当前工作区域，可以查看与恢复现场有关的内容，例如当前任务原始要求、相关文件或选中内容、工作 Agent 的对话入口和项目范围，但不默认复制整个 Agent 对话、终端输出和文件树。

> 当前工作区域是工作锚点，不是工作镜像。

它也帮助用户判断：一条理解现在会进入哪个 Agent、哪个项目和哪项工作；一份结果回来时，又属于哪里。

## 工作小浮窗的三个区域

这三个区域不必每次同时出现。哪部分有内容，才显示哪部分。

### 1. 当前工作

顶部保持一个足够轻的锚点：

```text
Codex
harness · 当前任务

讨论工作 UI 如何承接
```

收起时只保留 Agent 和项目，展开后才显示完整任务。用户能够确认 Trace 正在陪伴哪项工作，但不需要在这里管理任务进度。

### 2. 本次带回

这里不显示用户的全部历史，只显示过去形成、并与当前任务真正有关的少量内容。例如：

```text
本次带回 · 2

允许只留下一点触动，不强制整理成结论
用于：极简入口与保存流程

思考与工作不是两个分开的内容仓库
用于：悬浮窗与桌面端的接续
```

每条内容收起时先让用户认出：

- 这是什么理解、问题或尝试；
- 为什么与本次工作有关；
- 它准备怎样参与当前工作。

需要时再展开它来自哪里、当时为什么形成、适用范围和仍未解决的部分。用户可以直接说：

- “这次不用这个。”
- “它只是参考，不要当成要求。”
- “这一条只适用于当前项目。”
- “我以前的判断已经改了。”

不要求进入专门的上下文管理页面。

不同内容进入工作时承担的作用不同：

| 带回的内容 | 在当前工作中怎样出现 |
| --- | --- |
| 用户已经确认的取舍 | 可以参与当前方案与执行 |
| 尚未解决的问题 | 作为需要留意的地方，不当成工作要求 |
| 准备尝试的想法 | 显示这次想试什么、需要观察什么 |
| 外部案例 | 作为对照和来源，不等于用户立场 |
| 已经失效的理解 | 不再作为有效参考，只在追溯时可见 |
| 只在另一个项目成立的经验 | 说明范围，不自动套到当前项目 |

界面不一定显示一整套状态标签，可以用更贴近当前动作的表达：**这次会参考、这次准备试、只是作为对照、这次不使用。**

没有相关积累时，“本次带回”整个区域可以消失，工作正常开始，不用巨大的空状态催用户先去沉淀。

### 3. 工作中新增

用户选中一段 Agent 回复、代码、设计稿或原型区域，也可以直接说：

> 这个交互虽然轻，但是用户回来以后可能认不出来。先留一下。

产品形成一枚轻气泡：

```text
工作中新增

轻入口保存之后，用户可能认不出自己当时为什么在意。

来自：Codex · harness
悬浮窗原型讨论 · 刚刚
```

用户可以继续当前工作，不展开；也可以点击补一句、接到以前的一处问题、表示它只是当前实现问题，或者带到大浮窗继续讨论。

这里不生成完整工作复盘，也不因为一句“先留一下”，自动宣布它是一条长期经验。

## 工作气泡表示连接，不是重复 Agent 消息

普通代码生成、命令输出、文件修改和聊天继续留在原生 Agent 中，不全部堆入 Trace。

工作区域里的气泡主要表示三种连接：

1. **带进来的东西**：过去的一条取舍、问题或尝试与当前任务有关；
2. **工作中冒出的东西**：这里出现了一条值得留下的观察或冲突；
3. **带回来的结果**：之前准备尝试的东西，现在有了实际结果。

只有工作内容确实证明了一种做法、暴露一处冲突、改变用户判断，或成为以后恢复现场所需的依据时，才需要在 Trace 中形成一处可以继续的节点。

## 分清“带回了”与“真的起作用了”

“本次带回两条内容”，不等于它们已经帮助了工作。用户需要在必要时看清不同程度：

### 已带到本次工作

说明相关内容已经提供给当前 Agent。**已经送达，不代表已经采用。**

### 参与了本次做法

能够指出它影响了哪一处具体决定。例如：

> 因为“附言不应成为保存前提”，当前方案把附言设计成了可选展开项。

存在对应方案、Agent 决策、设计稿、代码位置或实际操作时，提供入口；只能确认送达，就不声称已经参与。

### 已经产生工作结果

例如交互已经做出来、方案已经调整，或者检查确认不填写附言也能完成保存。这证明工作产物发生了变化。

### 真实使用是否有效

用户后来是否真的更容易恢复当时为什么在意，还需要实际使用结果。不能因为实现完成，就标记为“理解已验证”。

界面用语应当尊重这些区别，例如：

- 已带入本次工作；
- 参与了这一处取舍；
- 已在原型中实现；
- 实际使用结果尚未回来。

不笼统显示“已应用”或“验证成功”。这些也不是要求用户逐步确认的流程，而是在需要追溯时能够如实说明。

## 当前要求与过去理解冲突时

如果当前用户明确要求“首页不要使用普通左侧栏”，而过去曾倾向“桌面产品需要固定侧栏承载导航”，本次明确要求优先。

小浮窗边缘可以安静显示：

> **本次要求与过去的一条判断不同**
>
> 这次将按“首页不使用固定侧栏”继续；过去的判断暂不修改。

用户可以继续工作、查看差异，也可以说“以后那条也改掉”或“只是在首页不用”。只有对象和影响范围不清楚时，才需要核对。

不能为了维护历史一致性，让用户停下工作进行一次理解审批；也不能背着用户按旧理解继续。

## 大浮窗：查看一次工作的接续轨迹

从工作小浮窗展开后，大浮窗不再复制成三栏聊天工作台，而是围绕当前工作表现：

**过去带入 → 本次正在做什么 → 实际怎样处理 → 出现什么结果或新问题 → 什么需要回到以后**

不一定画成固定流程图，也不要求所有部分同时展开。当前正在检查哪条理解有没有参与方案，就以那条理解及其对应做法为中心；正在带回实践结果，就以“上次准备试什么／这次实际发生什么／它可能改变什么”为中心。

其他历史、来源与修改过程按需展开，不固定铺在右侧卡片区。

## 什么时候进入完整桌面端

大浮窗仍围绕当前工作。只有用户需要下面这些跨工作操作时，才进入完整桌面端：

- 比较多个项目中的实践；
- 查看一条理解在哪些任务中被使用过；
- 修订以后多个工作怎样参考；
- 找回几次实践共同形成的变化；
- 查看分散在不同 Agent 中的相关工作；
- 整理自己的长期理解。

桌面首页可以轻轻显示一处正在发生的工作：

```text
正在发生

Codex · harness
工作 UI 如何承接
本次带回 2 · 工作中新增 1
```

但它不应变成多个 Agent 的监控仪表盘。点击后仍然进入刚才同一条接续轨迹，而不是重新打开一份 Trace 聊天。

## 一个用于继续推敲的小浮窗结构

下面只用于明确层级与动作，不是已经确定的视觉稿：

```text
┌────────────────────────────┐
│ Codex · harness             │
│ 当前：工作 UI 如何承接       │
│                         ↗  │
├────────────────────────────┤
│ 本次带回  2                  │
│                            │
│ 允许工作直接开始，不增加整理任务 │
│ 用于：不把 Trace 变成第二工作台 │
│                            │
│ 理解应当影响实际做法，而非只被读取 │
│ 用于：区分参考与实际影响        │
│                            │
│ 查看依据 · 本次排除           │
├────────────────────────────┤
│ 工作中新增  1                │
│                            │
│ 当前三栏结构把聊天变成了产品中心  │
│ 刚刚 · 来自本次界面讨论        │
│                            │
│ 先放着 · 继续想              │
├────────────────────────────┤
│ 补一句、纠正，或带回一个结果……   │
└────────────────────────────┘
```

实际界面不一定保留边框、分区和这么多文字。这个结构只是确认：顶部回答现在在哪里工作，中间回答过去带来了什么，下面回答这次又产生了什么，输入框允许自然地纠正、补充、留下和带回。

## 对应工作阶段的功能候选

| 工作中的需要 | 主要由什么承接 |
| --- | --- |
| 直接开始工作，不先整理 Trace | 当前工作区域；无相关内容时保持安静 |
| 让相关理解参与当前任务 | 本次带回；显示为什么相关和这次怎样使用 |
| 排除不适用内容或处理冲突 | 本次工作内直接调整，不自动修改长期理解 |
| 带着尚未成熟的想法试一次 | 本次带回中的“这次准备试”，保留理由和观察点 |
| 工作中有发现但没空展开 | 工作中新增气泡，连着必要现场先留下 |
| 实践后有了结果 | 接回原问题，分清事实、解释和准备怎样调整 |
| 修订以后怎样参考 | 用户明确修订后影响后续；本次例外不自动泛化 |

## 当前形成的工作 UI 判断

> 悬浮入口依附在当前原生 Agent 的工作现场；极简输入用于随时说一句；小浮窗显示当前 Agent、项目、任务，本次带回的少量相关理解，以及工作中新产生的气泡；大浮窗查看一次工作的接续轨迹；完整桌面端负责跨任务、跨时间和跨项目地寻找、比较与修订。

它让用户继续留在熟悉的 Agent 中做事，又能看见过去的理解怎样参与当前工作、这次实践怎样回到以后。工作 UI 是否足够轻、带回内容显示多少、不同宿主怎样保持一致，仍需结合后续 UI idea 和原型继续验证。
