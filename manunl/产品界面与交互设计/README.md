# 产品界面与交互设计

> 同一件事随着用户投入的程度逐渐展开，不要求用户先进入一个完整 App，才能得到帮助。

## 这一层属于哪里

这一文件夹属于产品的**界面与交互架构层**，位于[核心功能与内容对象](../产品功能与交互方案/核心功能与内容对象.md)和[功能候选与使用方式](../产品功能与交互方案/功能候选与使用方式.md)之后、具体页面草图与视觉实现之前。

| 层次 | 主要回答什么 |
| --- | --- |
| [产品定义](../产品定义.md) | 产品为谁解决什么问题，为什么值得做 |
| [产品交互链路](../产品交互链路/思考与学习阶段/README.md) | 用户处在什么情形，需要什么帮助，一轮之后怎样接续 |
| [产品功能与交互方案](../产品功能与交互方案/功能与交互骨架.md) | 需要哪些功能和交互行为，才能承接这些问题 |
| **产品界面与交互设计** | 功能出现在哪里，界面怎样逐层展开，不同载体各自承担什么 |
| 具体页面与视觉实现 | 页面如何构图、组件如何表现、动效与视觉语言怎样落地 |

这一层不重新定义产品方向，也暂不讨论 Skill、上下文包和宿主接入的技术实现。先确定用户实际接触产品时的空间、层级与动作，再由后面的原型验证它是否好用。

## 当前已经形成的两部分

- [整体交互形态](整体交互形态.md)：桌面悬浮入口怎样从极简输入、小浮窗和气泡，逐渐展开为大浮窗与完整桌面端；桌面首页为什么不应继续是普通聊天工作台。
- [工作阶段的原生 Agent 承接](工作阶段的原生 Agent 承接.md)：用户仍在 Codex 等原生 Agent 里工作时，怎样看见当前工作区域、本次带回的理解、实际影响和工作中新产生的变化。

两份内容不是两个独立产品。工作阶段使用同一套逐层展开的形态，只是围绕当前 Agent、项目与任务形成更明确的工作锚点。

## 接下来怎样承接零碎的 UI idea

后续的截图、一句话、局部交互和视觉形式，可以先留在这一层继续讨论，不要求一开始就完整，也不需要先归到某个功能模块。

讨论时再判断：

- 它发生在悬浮入口、小浮窗、大浮窗还是桌面端；
- 它帮助用户完成了哪一段交互链路；
- 它是否让同一件事更容易继续，而不是增加一个孤立页面；
- 操作之后什么发生变化，收起、接错或不想继续时怎样退回来；
- 它是整体交互架构的一部分，还是只属于某个具体页面或视觉风格。

暂时接不上的形式也可以先保留。如果它揭示了尚未覆盖的真实需要，再回到功能候选补充，不为了保持现有清单完整而硬塞进去。
