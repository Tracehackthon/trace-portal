# 工作阶段

> 我正在做一件事，先帮我把它做好，别让我为了使用你的产品再多做一件事。

本篇整理已经讨论过的工作链路，先围绕“正在做一件事时”展开，不预先补齐其他时期。下面的开发场景用于说明产品怎样帮助，不代表功能已经实现或经过使用验证。

## 核心

- **先服务眼前的工作，不要求用户先去整理知识、定义能力或完成学习。**
- **让相关的既往理解与经验影响实际做法和结果，而不只是成功带回一条记忆。**
- **工作本身也会产生新的理解，但不把每次工作都变成一项沉淀任务。**

从当前要做的事情进入 → 按需带入相关理解与经验 → 在实际推进中起作用 → 遇到变化时帮助处理 → 将值得继续的部分留下

这是一条帮助主线，不是固定流程。没有相关历史时，工作正常开始；没有值得沉淀的新发现时，也允许做完就结束。

## 与思考与学习阶段的关系

[思考与学习阶段](../思考与学习阶段/README.md)可能从“这里有些东西，我想弄明白”开始，也可能还不知道究竟想问什么。

工作阶段先围绕“我正在做一件事，怎样把它做好”。用户可以直接开始工作，不必先经过思考与学习阶段；工作中出现值得深想的问题，也可以再转回讨论。

不应该要求用户先到 Trace 整理理解、整理成能力，再去工作，做完之后还要回来交一份复盘。

## 用户、工作 Agent 与 Trace 各自负责什么

这里先从用户与原生 Agent 一起工作的情况进入，不把工作限定为写代码。写方案、做研究、修改设计，也可能遇到同样的问题。

| 参与者 | 主要负责什么 |
| --- | --- |
| 用户 | 决定这次要做什么、哪些取舍仍然成立，也可以改变主意 |
| 工作 Agent／原有工具 | 理解当前任务，执行、检查并交付 |
| Trace | 让相关的既往理解与经验被恰当地使用，并接住需要保留的新变化 |

Trace 不再接管一遍工作，也不让用户为了接续背景换到另一个聊天窗口。当前任务的推理与执行仍由工作 Agent 和原有工具承担。

## 正在做一件事时

### 从当前要做的事情进入

> 我仍然在熟悉的地方正常工作，不需要先完成 Trace 的一套准备流程。

- 先接准用户这次想做什么，利用已有的任务、材料和工作现场，不重新盘问已经说清的背景。
- 在用户授权的范围内，按这次需要找相关理解，不把所有历史都带进来。
- 过去形成的理解，要结合当前任务要求与现场条件判断，不因为以前采用过就默认这次必须照做。
- 没有相关积累时，不强行找关联，也不要求用户先补一轮学习。

#### 用户的感受

> 我可以直接开始做事。产品知道什么时候能帮一点，什么时候应该让工作正常继续。

### 让相关理解参与这次执行

假设用户对工作 Agent 说：

> 帮我实现用户把知乎里有触动的一段内容留下来的交互。

Agent 可能做出收藏入口、自动摘要、标签分类和知识卡片。它完成了字面任务，但用户仍然需要纠正：

> 不是这个意思。我们之前已经讨论过了，我不想让每次触动都变成标准摘要，也不想要求用户立刻整理成结论。

这里损失的不只是重新输入背景的时间，而是之前已经想清楚的东西，没有影响这次实际做出来的东西。

- Trace 在这次需要时带入相关取舍，例如“允许只留下一点触动就离开”“不要把不同思考都加工成同一种摘要”。
- 说明它们为什么与眼前任务有关，让工作 Agent 结合当前材料和条件决定怎么实现。
- 提出的建议、暂存的想法和用户已经认可的理解要分清，不把尚未确定的想法当成工作要求。
- 是否帮上忙，要看实际做法或结果有没有因此改变，不能只看历史有没有被读取。

#### 用户的感受

> 之前讨论过的取舍，真的影响了这次做出来的东西，而我不用再解释一遍。

### 我正在推进，别不停打断我

- 相关理解能够直接帮助执行，就尽量在执行中起作用，不必每一条都弹出来要求用户回应。
- 如果旧理解与这次明确要求冲突，就指出真正影响工作的差异，不能偷偷按旧理解做。
- 用户可以改变主意，也可以排除这次不适用的经验；历史不是用来约束用户的。
- 不为了体现产品存在感，在正常推进时不断建议讨论、找反例或整理收获。

安静不是不透明，也不是替用户做重要决定。

#### 用户的感受

> 我可以保持工作的节奏；真正需要我判断时，产品会把关键冲突说清楚，而不是一直让我确认小事。

### 在做的过程中，发现之前想的不对

例如，真正试用交互后，用户发现：

> 完全不让用户表达在意之处，虽然保存很轻，但后来确实很难接回来。

这不应该立刻被改写成“以后必须填写收藏理由”。先分清：

- 是这个具体实现没有做好？
- 是原来的判断需要补充条件？
- 还是原来的方向确实需要调整？

先帮助处理眼前的问题，再判断其中什么值得影响以后。

- 把新发现与当时的条件、做法和结果放在一起看，不只留下抽象结论。
- 可以支持原理解、缩小适用范围，也可以提出需要撤回或修正的地方，由用户决定。
- 一次局部修补不自动变成长久规则，工作完成也不等于相关方法已经得到普遍验证。

#### 用户的感受

> 实际做过之后，我可以修正以前的想法；产品不会把一次临时处理偷偷变成以后都要遵守的规则。

### 现在没空展开，但不想把这个想法丢掉

> 我正在赶进度，发现了一个值得深想的问题，但不想现在转入讨论。

- 用户想留下时，接住这个问题和必要现场，让当前工作继续，不要求立刻整理成完整结论。
- 之后愿意讨论时，能够知道当时为什么冒出这个问题、它与哪一处工作有关，不只剩一句脱离背景的话。
- 是否继续讨论、是否改变以后的做法，由用户决定；留下不等于已经采用。
- 不把每次工作对话全量变成待处理材料，也不强制工作结束后复盘。

#### 用户的感受

> 我不用在“现在停下来想清楚”和“以后彻底忘掉”之间二选一。

## 这一阶段要真正帮上的忙

> 我仍然在熟悉的地方正常工作，但少重复解释了一些东西，少走了一段已经走过的弯路，或者终于让已有理解影响了眼前的结果。

先看这次工作是否因此做得更合适，再看有没有值得继续思考的东西。没有新发现也可以结束，不需要为了证明使用过 Trace，再生产一份笔记或复盘。

“工作过程中可以沉淀什么”是后续要承接的事，不能盖过“先怎样帮我把眼前的事做好”。

## 实践想法怎样继续

工作中留下的想法，以及做过之后结合情形形成的判断，如何重新拿起并继续变化，见[实践想法的接续](实践想法的接续.md)。这里不只停在“先留下”，也要让新的实践结果有机会反过来修正理解。
