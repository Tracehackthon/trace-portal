# 功能与交互骨架

> 产品的具体功能、UI 交互，如何解决产品交互链路中那些需要解决的问题。

这是涵盖思考与学习阶段、工作阶段的共同讨论底稿，用来承接后面的具体功能和 UI idea。现有做法仍是候选方案，还没有定死页面数量、布局、组件或技术实现，也不代表功能已经实现或通过使用验证。

先把两个阶段需要什么帮助、怎样接续放在同一个骨架里，再慢慢讨论具体做法。工作阶段不只是使用过去的理解，还包括工作中产生的新想法，以及做过之后带着实际情形重新判断。

进一步讨论形成的第一版[功能候选与使用方式](功能候选与使用方式.md)已经单独整理，包含两个阶段的具体使用动作、贯穿其中的交互能力，以及与原链路的对应。在此基础上，[核心功能与内容对象](核心功能与内容对象.md)进一步把详细候选收束为“留下一点、从这里接着、找个对照、我的理解、带去用、结果回来”六项核心功能，并明确它们共同围绕的内容对象。本篇保留整体骨架；悬浮入口、小浮窗、大浮窗、桌面端和原生 Agent 的承接进入下一层[产品界面与交互设计](../产品界面与交互设计/README.md)继续展开。

## 这一份属于哪一层

| 层次 | 主要回答什么 |
| --- | --- |
| 产品定义 | 为谁解决什么问题，为什么值得做 |

本篇位于“功能与交互方案”这一层，依据[产品定义](../产品定义.md)和已经讨论的链路展开，不重新定义产品方向。[思考与学习阶段](../产品交互链路/思考与学习阶段/README.md)与[工作阶段](../产品交互链路/工作阶段/正在做一件事时.md)分别保留对应的用户处境与帮助主线。

现在开始想功能和 UI，不是在偏离产品重心，而是在把前面说清的帮助兑现。功能和 UI 可以一起推敲，不必先把功能清单全部写完，再给它套界面。

## 两个阶段分别先服务什么

| 阶段 | 用户此刻的需要 | 功能与交互首先要承接什么 |
| --- | --- | --- |
| 思考与学习阶段 | 这里有点东西，我想留下、弄清楚，或者用自己的话整理 | 轻轻接住现场，帮助理解、表达和对照；回来时能继续想，而不只是再看一遍 |
| 工作阶段 | 我正在做一件事，先帮我把它做好 | 从当前任务进入，让相关理解影响执行，不打断正常工作；接住实践想法，并让后来结果继续参与修正 |

- 用户可以直接开始工作，不必先读文章、讨论或整理 manual。
- 思考与学习也不一定要进入工作，分清一个区别、形成一个问题本身就可以有收获。
- 两个阶段不是两个互不相通的内容仓库，也不是必须手动切换的两种模式。阅读可以进入实践，工作中的想法也可以回来讨论。
- 下面先讨论共同的交互位置，同时保留不同现场的做法；不把同一种界面强行套在两个阶段上。

## 从问山借鉴的交互接续

参考[问山 ThreadPeak](https://threadpeak.wuxianming.ac.cn/)，依据本轮提供的产品说明截图。这里借鉴的是设计说明中的机制，不把说明当成实际操作效果已经验证。

| 用户遇到的问题 | 说明中的功能与交互怎样承接 |
| --- | --- |
| 不知道哪条学习路线适合自己 | 通过目标输入和简短访谈明确条件，再生成路线 |
| 阅读中有一处不明白 | 从具体文章或知识卡发起追问，解释沿着原节点继续，不覆盖原文 |
| 学习、材料和实践容易散开 | 文章、追问、实验记录落在同一条知识脉络中 |
| 继续问 AI 也解决不了 | 展示相关创作者的经验依据，提供可编辑的请教草稿，是否联系由用户决定 |

值得借鉴的不只是下一步有按钮，而是每一步都接着上一步留下的东西。

Trace 不直接照搬“目标 → 路线 → 节点”，因为用户也可能只是被触动，暂时没有目标。3D、卡片或其他形式，要看它是否真的帮助用户理解和操作，不因为别人使用就成为我们的必需项。

## 围绕用户正在在意的“这件事”接起来

> 材料、讨论、自己写的理解和后续变化，可以围绕用户在意的同一件事继续生长。

例如：“为什么我收藏了很多文章，却还是觉得没有收获？”

围绕这件事，可能先有一段知乎原文，然后有一次讨论，后来用户自己写了一句话，又从另一篇文章里发现反例。

- 不应该让收藏、聊天、manual 和新发现各自散在互不相通的地方。
- 可以保留不同的内容形态，但用户能认出“我仍然在继续同一件事”，也能从理解回到相关讨论和来源。
- “这件事”暂时只是帮助我们设计的说法，不急着定正式产品名称。
- 随手留下片段时，不必立刻建立主题、命名、分类；等用户真的开始继续想，再逐渐组织起来。
- 无关的新发现可以另起一条，不为了组织完整而强行连接。

工作中的原型、方案、使用结果，也可以成为这件事的现场和依据。但工作任务与持续思考不能完全等同：任务承接进度和交付，实践问题承接为什么这样做、后来怎样理解。两者需要能关联，不是每个任务都自动生成一条思考；任务做完了，也不代表相关问题已经想完。

## 两个阶段共用的三个交互位置（候选）

这三个位置不是三个必须经过的页面，也不意味着要重新做一个独立聊天产品。在原生 Agent 中，优先利用现有讨论和执行现场；在阅读现场，再考虑合适的伴随入口。暂时用这三个位置检查两类场景是否接得上，不把它们当成已经确定的信息架构。

### 在原现场：一个足够轻的入口

#### 阅读中留下触动

> 我正在阅读，看到一段有触动的内容，先别丢。

以知乎阅读为例，用户选中一段话后，可以从当前现场的轻入口“留一下”，不必马上跳到 Trace 首页。

#### 用户看到和能做什么

- 看见刚才选中的原文、作者和原文入口，不用重新搬运背景。
- 可以补一句“这里让我想到……”，但附言不是必填项。
- 留下后有清楚的反馈，也能撤销；不要求填标题、选分类，不默认生成长摘要。
- 只是怕丢，到这里就结束；想继续时，再从这个片段打开讨论，原文仍然容易找到。
- 进入讨论后，选中的片段已经作为来源附在当前问题上，不用重新复制粘贴。

#### 用户的感受

> 我只是把一个触动交进来，不需要先学会你的一套整理方式，也不必立刻把它加工成结论。

这里是候选交互，不预先承诺所有平台都能原地划选接入。浏览器扩展、分享入口或复制链接，需要按实际宿主能力决定。

#### 正常工作，直接从当前任务进入

> 我现在要做这件事，不是先来保存一条想法。

- 用户在熟悉的工作 Agent 或工具里继续，不必先到 Trace 新建主题、搬运任务或整理能力。
- 按当前任务需要，在授权范围内带入相关理解和经验；没有相关积累就正常开始，不强行关联。
- 当前任务的推理、执行和交付仍由工作 Agent 与原有工具承担；Trace 提供接续，不另行接管一遍工作。

#### 工作中冒出想法，先接住必要现场

> 这里好像和我之前想的不一样，不过现在先把事情做下去。

- 可以直接说“这个先留一下”，或者选中相关片段留下，不要求转去另一个窗口写完整笔记。
- 连着必要的任务片段、原型或结果留下“发生了什么、当时想到什么、还没分清什么”；能利用现有上下文就不让用户填表，缺少依据的部分不编造。
- 会影响当前做法，就在工作里处理；暂时不展开，就让工作继续。留下不等于采用，也不自动变成复盘待办。

### 围绕“这件事”：能讨论，也能自己动手的空间

> 我想顺着它弄清楚一点，也想有地方用自己的话整理收获。

用户决定展开后，需要能分清三样东西：

- **我们正在谈什么**：当前问题，以及相关原文或实践现场。
- **我们怎么谈到这里**：讨论过程、追问、对照，以及当时做法和结果。
- **我现在怎么理解**：用户能够亲自写、改、保留未决的 manual 内容。

它们不一定是三个一直展开的栏位。可以围绕当前活动按需展开，重点是能互相定位，而不是同时塞满屏幕。

#### 用户看到和能做什么

- 对照原文继续讨论，需要时能回到具体来源，而不只看到 Agent 的解释。
- 从一段有帮助的回复中选出需要的部分，放到“我的理解”里，不把整段回答一律存成结论。
- 内容进入可编辑的位置，用户可以用自己的话修改，也可以暂时保持为草稿。
- 保留它来自哪段讨论的入口，分清“暂时留下”和“作为后续参考”。未确认的解释不自动成为用户观点。
- 用户也可以绕过聊天，直接在 manual 中写；修改、删除或限定理解后，后续接续要跟着变。

#### 工作中的想法回来时

- 先恢复上次停在哪里，再呈现这次真实带回的新结果，不默认展开全部历史；没有新增内容就不编造。
- 有结果时，对照发生的事、用户对原因的解释和准备怎样调整，不把猜想直接写成结论。
- 没有结果但想继续时，可以带来一个具体情境作比较，也可以让用户自己写；想直接尝试时，把问题和适用条件交给当前工作，不要求先写成完整方法。
- 用户愿意留下的变化，更新同一件事的当前理解或未决部分，并保留形成过程；不只追加一份独立总结，也不把临时尝试自动升级为长期规则。

#### 用户的感受

> 我不只是收到一个答案，我有地方把它变成自己能修改、能继续想的东西。

### 回到阅读或工作现场：按需接续，并接回新的变化

> 我后来又遇到了相关的东西，之前想过的部分能不能在这次帮上忙？

#### 再次阅读时

存在相关思考时，可以出现一条可忽略的关联提示。例如：

> 可能接上你之前在想的：收藏为什么没有变成收获。
>
> 这段材料讨论的是“留下自己的理解”，可能补充你之前区分的两种收藏方式。

- 用户可以接着看，也可以表示“这次无关”，不因为关键词相同就自动合并。
- 进入后先恢复上次已经分清的地方、仍未弄明白的地方，以及这次的新材料，不默认展开全部历史。
- 用户可以从这里继续，也可以先看这次材料，暂时不带回旧理解。

#### 正常工作时

- 在原生工作 Agent 中采用更安静的伴随形式，例如可展开的“本次参考”，不另起一套必须经过的工作流程。
- 说明本次带入了哪些理解、为什么相关、适用于哪里，允许排除不适合的一条。
- 没有相关历史时，让工作正常开始，不为了表现产品存在感而强行关联。
- 旧理解与本次明确要求发生冲突时，指出真正影响工作的差异，不偷偷按旧理解做。
- “已提供给 Agent 参考”与“已经影响实际结果”要分清。不能只注入了上下文，就显示“成功应用”。

#### 实践之后，重新拿起或带回结果

- **主动找回来**：从事情列表、检索或一句自然语言进入，让用户能认出上次停在哪里，不只显示文件名和更新时间。
- **当前工作正好相关**：提示具体关联，允许继续、忽略或排除，不自动套用未确认的办法。
- **直接带回新结果**：用户说“上次那个问题，我试过了”，就能从当前现场接回原来的事情；对应不清楚时先核对，不要求手工寻找后复制。
- 回来之后能补事实、自己写、修正理解或带去尝试；结果回到同一件事，供以后继续。用户只是想回看或暂时不想继续，也可以结束。

这三个入口可以接到上面的讨论与整理空间，不各建一套独立内容。详细链路见[实践想法的接续](../产品交互链路/工作阶段/实践想法的接续.md)；这里保留要由具体交互承接的部分。

#### 用户的感受

> 之前想清楚的东西能够影响眼前的事情，而我不必再解释一遍；这次想法变了，也能由我决定怎么改。

> 工作中新冒出的想法也不只停在“先留下”。我能从后来的结果接着想，并让变化影响下一次。

## 跨时期的处境，怎样落到交互上

思考与学习的具体处境见[跨时期的理解处境说明](../产品交互链路/思考与学习阶段/README.md)，工作中的处境见前述工作链路。这里一起保留对应的交互候选，不为每一种情况新增独立模块。

| 用户的处境 | 可以怎样落到交互上 |
| --- | --- |
| 还在意，但想不出怎么继续 | 需要时带来一个具体情境或反例，让用户针对它判断，而不只留下“继续提问”的空输入框 |
| 跟着解释懂，自己判断时又断了 | 在相关解释处提供“换个例子让我试试”，先留出自己判断的空间，再针对实际断点回应 |
| 聊着聊着，关心的事情变了 | 确实需要确认方向时，允许把新问题作为接下来讨论的中心，不一直拉回原主题 |
| 想重新阅读，不想先受旧结论影响 | 先围绕这次材料和感受展开，需要比较时，再把过去与现在放在一起 |
| 正在工作，不想被接续功能打断 | 可以查看本次参考，也可以排除不适用的内容；只把真正影响当前做法的冲突交给用户判断 |
| 实践中有想法，但现在没空展开 | 从现场轻轻留下相关片段和问题，不强迫转入深度讨论或工作后复盘 |
| 做过之后有新判断，想让它影响以后 | 从结果接回同一件事，区分事实、解释与尝试，用户自己写或认可后再更新当前理解 |

这些操作不全部常驻在输入框上方，也不把产品方法论变成一排按钮。它们应当在具体处境中出现，可以忽略，也允许用户直接用自然语言表达。

## 两个阶段都要贯通的体验

先用下面两条候选体验分别检查骨架，不把工作只当作阅读之后的最后一步。这不是本轮已经验证通过的流程，也不要求用户把每一步走完。

### 从思考与学习进入

知乎原文中的一个触动 → 原地留下 → 围绕它讨论 → 自己整理一处理解 → 后来从新的现场接回来

这是先刻画的一条体验，不是要求每次使用都跑完。工作阶段可以接着使用同一份理解，而不是另建一套互不相通的内容。

> 我留下一段触动，没有被要求整理；后来顺着它讨论，自己改出了两句话。几天后，另一篇文章让我有了新发现，我能看见它与之前哪一处有关。再后来正常工作时，那两句话真的影响了做出来的东西，而我没有重新解释一遍。

### 直接从工作进入

当前任务 → 按需参考已有理解 → 推进中出现实践想法 → 当场处理或先留下 → 带着实际结果回来 → 更新理解、问题或尝试 → 在下一次相关工作中继续起作用

> 我直接开始做事，之前确认过的取舍在需要时参与了这次执行。做的过程中发现一个不对劲的地方，我先留下，工作没有被迫停下。后来试过，有了新的结果，我不用翻遍聊天就能接回原来的问题；这次分清的东西也不是只多出一份总结，而是能帮助下一次做得更合适。

这里也允许没有历史、没有新想法、没有事后整理。产品不能为了跑完整条链路，给用户再制造一项工作。

想要的 wow 不只是生成了一张复杂的图，而是：

> 原来我随手留下的东西，真的一路跟到了这里；而且沿途一直允许我参与、修改和改变方向。

这仍然是希望实现的体验，需要通过具体原型和使用过程验证。

## 接下来慢慢讨论，还没有定下来的地方

- **现场与空间怎样衔接**：原生 Agent、阅读现场与自己整理的空间，哪些内容原地完成，哪些需要展开；不先假定都要跳转到 Trace。
- **不同内容怎样放在一起**：原文、讨论、manual、工作结果如何互相定位，又不把“这件事”变成另一个杂乱文件夹或聊天列表。
- **参考与变化怎样让用户看清楚**：怎样区分暂存、当前理解、这次参考和实际影响，既允许修改与排除，又不增加一堆确认按钮。
- **回来后的下一步怎样自然发生**：回看、补充、自己写、对照和尝试如何在同一件事上接续，而不是打开后只剩一个空输入框。

这几处的功能行为已在[功能候选与使用方式](功能候选与使用方式.md)中继续补清，具体界面怎样承接仍需结合 UI idea 讨论，没有定死。看到别人的做法，可以先记它解决了哪个处境，再回来比较是否适合 Trace；有意思的形式也可以先留着，不必马上采用。

## 接下来刻画具体功能和 UI idea

后续按具体体验分别展开，例如“阅读现场如何留下”“讨论与自己整理如何衔接”“工作中怎样参考与先留”“实践结果怎样接回来”，不先按按钮、卡片、侧栏分类。

每个 idea 可以从这些问题往下画：

- 用户此刻在哪里，想解决什么？
- 他看见什么，能做什么？
- 操作后，内容和状态发生什么变化，用户怎样知道结果？
- 不想继续、想撤销或操作失败时，怎样不丢掉已经做的事情？
- 下次要接着用时，从哪里回来，接回什么？

不要求每个灵感一开始就写完整。先允许草图和局部想法，再用这些问题检查它到底接住了哪一段需要。

功能与交互骨架负责让各个 idea 接得起来；具体 UI idea 负责把其中一段帮助做得清楚、顺手、有感受。
