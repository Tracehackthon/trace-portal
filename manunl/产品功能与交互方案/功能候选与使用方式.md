# 功能候选与使用方式

> 产品的具体功能、UI 交互，如何解决产品交互链路中那些需要解决的问题。

这是在[功能与交互骨架](功能与交互骨架.md)上继续讨论形成的第一版功能候选，涵盖思考与学习阶段、工作阶段，供接下来推敲具体功能和零碎的 UI idea。当前已经由[核心功能与内容对象](核心功能与内容对象.md)把这些详细行为正式收束为六项核心功能；本文继续保留各类真实处境、行为边界和与原链路的对应，不改写成只有名称的功能清单。

先讨论用户看见什么、能做什么，以及操作以后是否真的得到帮助，暂不展开技术底层。这里保留的是已讨论的行为方向，不代表功能已经实现或通过使用验证，也没有定下页面数量、布局和组件。

编号方便逐项讨论，不是要求用户按顺序完成，也不代表要做这么多个页面。用户可以从阅读、一个模糊想法、自己写的内容或当前工作直接进入，也可以随时先停。

## 在阅读、思考与学习的时候

### 1. 带入材料，随手留下一点

用户正在知乎阅读，可以选中一段内容“留一下”，也可以带入链接、文件，或在授权范围内选择已有收藏。没有材料时，也可以直接写下一句模糊想法。

留下原片段、来源和必要现场；用户愿意就补一句“这里让我想到……”，不要求填写标题、分类或完整收藏理由。保存后能确认留下了什么、可以撤销，也可以直接离开。

**想展开时，从留下的具体片段继续，不用重新搬运背景。**

### 2. 围绕具体一处展开讨论

用户可以针对原文、自己写的一句话、Agent 的一段解释发问，也可以只说“这里让我有点说不清的感觉”。

讨论从这个具体位置出发，帮助分清一个冲突、一个概念或一处缺失的依据，而不是一上来给整篇总结。解释与原文能够互相定位，用户可以随时纠正、追问或提出不同看法。

**这一小轮的结果，可以只是问题变清楚了一点，不必生成结论。**

### 3. 找到有用的对照与请教线索

用户说“有没有人遇到过类似情况”“找个反例看看”，产品围绕当前缺口寻找材料，包括自己的既往思考，以及知乎等来源中的相关经验。

不只展示相似文章，还说明：

- 相似的是哪一处；
- 对方的条件与自己有什么不同；
- 它补充或挑战了当前哪段思考；
- 哪些是原文内容，哪些只是 Agent 的推断。

需要进一步请教时，可以从具体材料找到相关创作者，并整理可编辑的提问草稿。**有公开相关经验，不等于对方一定能解决或愿意提供服务；是否联系由用户决定。**

### 4. 换个情形，自己试着判断

用户想继续却提不出问题，或者发现“听解释时懂，自己判断时又不会”，可以让产品给出一个贴近当前问题的具体情形。

两种情况，帮助方式略有不同：

- **想不出怎么继续**：找一处尚未被具体情境检验的设想，提供一个可供判断的案例。
- **独立判断时断了**：先让用户说出自己的判断，再针对实际混淆的一处补解释。

不急着展示完整答案，不强制考试、评分或每次复述；没有触动也可以停。真实案例与用于推敲的假设情境要分清。

**它要提供的是一个能继续思考的对象，而不是更多等待阅读的解释。**

### 5. 自己写，也可以请 Agent 帮着整理

用户可以绕过聊天，直接在自己的整理空间里写；也可以把讨论中的一部分接到已有内容里。

需要帮助时，可以说：

> 把刚才分清的两点接到这里，保留我的表达，没确定的别写死。

产品根据实际内容帮助组织：问题判断保留依据与未决点，做法保留适用条件和检查方式，领域理解保留概念关系，触动可以仍然只是一个片段。

**不强制选类型，不统一加工成摘要，不因为进入 manual 就当作已经认可。** 用户可以只写一半，也可以拒绝 Agent 的修改。

从讨论里拿出一部分时，保留相关出处，能接到用户指定的位置，不顺手重写原来的全文。与原内容有冲突，就指出冲突，不擅自把两种说法揉成一个看似一致的结论。

## 离开之后，重新拿起的时候

### 6. 找回上次停在哪里

用户可以从列表、搜索或一句自然语言找到之前的事情，例如：

> 找一下之前那个收藏后为什么接不回来的问题。

入口不只显示名称和更新时间，还要让用户认得出：当时为什么在意、已经分清什么、停在哪一处。需要追溯时，再打开原始讨论和来源。如果后来改过想法，能分清当时与现在，不把不同时间的说法混在一起。

用户已经忘记时，也可以在后来相关的阅读或工作中，收到一条说明具体关联的轻提示；不因为很久没打开就催促复习。

**回来后可以继续讨论、自己修改，也可以只是看明白后离开。**

### 7. 把新发现接到之前的一处思考

用户带来新文章、新感受或新问题时，不必先找到旧记录再复制进去。

如果确实相关，产品帮助指出：

> 这段材料补充了你之前没有分清的这一处。
>
> 这个情况可能限制了原判断的适用范围。

用户可以沿着它继续、保留为另一种解释，或表示“这次不是那件事”。**有关联，不等于自动合并；有反例，也不等于立即推翻。**

愿意留下的进展接回原来的理解或未决问题，不再散成一份彼此独立的新总结。只是表面相似，或者本来就在讨论另一件事，就允许另起一条，不强行连接。

## 正在正常工作的时候

### 8. 让相关理解参与当前工作，并能查看、调整本次参考

用户仍然在原来的 Agent 或工具里开始工作，不需要先到 Trace 新建主题或整理能力。

相关的既往理解按需参与当前任务。例如，之前已经确定“不强迫用户把触动整理成结论”，这次设计收藏交互时，就应当影响具体取舍，而不是还要用户重新解释。

需要查看时，用户能看见本次参考了什么、为什么相关、适用于哪里，并能排除不适用的内容。发生真正影响工作的冲突时，再明确指出。

**提供了参考、参与了方案、落实到了产物，要按实际证据区分；没有历史时，工作照常开始。**

当前任务的推理、执行、检查和交付仍由工作 Agent 与原有工具承担，Trace 不再接管一次工作。有对应的方案、产物或检查结果，就提供入口；只能确认提供了参考，就只说提供了参考。交互做出来了，也不等于已经解决真实使用中的问题。

### 9. 带着一个尚未成熟的想法试一次

用户在讨论或自己整理时说：

> 先不用继续想了，把这个带到当前原型里试一下。

当前工作接走的不只是一个动作，也包括与这次尝试有关的问题、理由、已有取舍和未确定之处。已知的观察重点一并带上，不要求用户先写成完整方法，也不为没有依据的部分编造内容。

此次尝试与原问题保持关联，后面可以接回结果。**试用不等于长期采用，也不要求每次工作都带着一个研究问题。**

### 10. 留下工作现场的新发现，不打断当前工作

工作中冒出一个实践想法，用户可以选中相关位置，或直接说：

> 这里有点不对，这个先留下，眼前的先继续。

产品接住这句话以及必要的任务片段、方案或结果，让用户以后能恢复它为什么在当时出现；观察到的事实与猜测分开，不替用户编造原因。

会影响眼前做法，就当场处理；暂时不展开，就先保留。**不把“先留下”变成待办催促，也不要求做完之后交一份复盘。**

### 11. 带着结果回来，继续比较、修正或尝试

用户可以直接说：

> 上次那个我试过了，实际情况和我们想的不一样。

产品接回对应问题，先恢复上次的判断或尝试，再加入这次实际带回的结果。帮助区分发生了什么、可能怎样解释，以及它支持、限制或挑战了什么。

用户可以从这里继续讨论、修改自己的理解，或再尝试一种做法。任务结束了，问题仍然可以继续；一次成功，也不自动证明方法普遍成立。

**没有拿到真实使用结果，就不能把“工作完成”自动写成“想法得到验证”。** 没有新结果时，不编造“这次新增”，仍然可以回来阅读、继续想或先停。

## 必须贯穿这些功能的四项交互能力

这些不必各做一个模块，但缺少任何一项，前面的功能都会出现断点。能用清楚的状态和就地标注解决，就不要不断弹出问题；提示有具体触发、有明确帮助，也可以忽略。

### 随时纠正、暂停、留下旁支或改变方向

- **接错了**：修正当前理解，后续回应跟着变，不要求重新交代全部背景。讨论中的临时理解，不直接等同于用户已认可的长期理解。
- **先停**：保留已分清的地方与真实停点，不强行收成结论，也不把暂停后的接续信息自动变成 manual 中的正式判断。
- **留下旁支**：保留来处，当前讨论继续。
- **改变方向**：允许新问题成为主线，旧问题可以暂停，不要求先完成旧问题。细化同一件事不必另起一条，确实是另一件事再分开。

**“先收着”和“接下来沿这个想”，必须产生不同结果。** 用户可以直接用自然语言表达，不必每次学习和选择分类。

### 关联可以被拒绝和修复

用户可以说“这次无关”“不是这个问题”“把这段接到另一处”。对应不清楚时先核对，不清楚也可以暂时不关联。

修复时不丢掉原始材料或结果；解除错误关联，也要处理由它产生的错误解释。如果已经影响了用户保存的理解，需要指出受影响的位置，由用户决定怎样修订，而不只是挪动界面上的归属。

同一份材料或结果可以与多处问题有关，分别说明关系，不必复制成互不相通的多份内容。

### 用户的修改，要影响后续怎样参考

用户自己写的、Agent 建议的、尚未确定的，以及已认可的理解，需要能分清，但不必靠一套繁琐审批流程表达。

按照已经讨论的默认：

- **明确修改未来理解且对象、范围清楚**：修订并展示改了哪里，允许撤销；有歧义时才进一步核对，不每次重新问“是否确定保存”。
- **只是这次例外**：不自动改变长期理解。
- **删除、停用或限定范围**：后续参考跟着变，不再从旧摘要里重新带回已经失效的判断。
- **留下一次猜想或尝试**：不自动升级成执行要求。

编辑原本已经用于后续参考的内容，保持其原有适用范围，不要求每次小改都重新确认；编辑草稿，仍然是草稿。新的解释也可能只是另一种可能，不自动替换原理解。

如果某项工作已经拿到了旧理解，后来理解才被修改，需要让受影响的当前工作知道具体变化，再决定是否调整；不把修改理解等同于已经自动纠正所有进行中的任务，也不擅自重做已完成的产物。

个人修改不能静默变成团队规则，个人、项目与团队的范围不能自动扩大。

### 能接回历史，也允许暂时不让历史带路

用户想从以前继续，就及时恢复相关进展。

用户想重新阅读、先表达这次的感受，就先围绕眼前内容展开，等需要比较时再带回旧理解。**不是只把历史面板收起来，却仍然用旧结论替用户解释新感受。**

## 接下来承接零碎的 UI idea

> 随手交进来的东西，能帮助我往前想；已经想清楚的东西，能帮助我眼前做事；后来有了变化，也能接回去。

后面刻画 UI，围绕这些具体动作展开，不先决定要做多少卡片、侧栏或知识图谱。

当前已经进入下一层[产品界面与交互设计](../产品界面与交互设计/README.md)，先形成了悬浮入口到桌面端的整体展开形态，以及工作阶段在原生 Agent 中怎样承接。后续 UI idea 可以沿着这一层继续补充和修正。

截图、一句话、局部草图都可以先带进来，不要求每个 idea 一开始就完整。先保留有意思的那一处，再看它承接哪段功能、操作以后用户多得到了什么、怎样接到前后一步。不把这些检查变成用户提交 idea 前必须填完的表单。

暂时找不到对应位置的形式，也可以先留着，不急着采用或否定；如果它揭示了尚未覆盖的真实需要，再回头补功能候选，不为了塞进现有清单而硬归类。具体承接时沿用文件夹和文件区分，不预先铺开一套还用不上的页面或目录。
